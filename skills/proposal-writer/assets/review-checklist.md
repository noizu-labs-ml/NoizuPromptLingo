# Proposal Review Checklist

Run this before every submission. One missed Critical item can kill a deal or create a contract dispute.

**Proposal:** _______________________________________________
**Client:** _______________________________________________
**Reviewer:** _______________________________________________
**Review Date:** _______________________________________________
**Version:** _______________________________________________

---

## Category 1: Structure

| # | Check | Severity | Pass |
|---|-------|----------|------|
| 1.1 | Executive summary is present and ≤ 3 paragraphs | Important | [ ] |
| 1.2 | Problem statement clearly articulates the client's pain | Critical | [ ] |
| 1.3 | Proposed solution section is present | Critical | [ ] |
| 1.4 | Deliverables section is present and detailed | Critical | [ ] |
| 1.5 | Timeline is present (weeks or dates, not vague ranges) | Critical | [ ] |
| 1.6 | Pricing / investment section is present | Critical | [ ] |
| 1.7 | Assumptions section is present | Critical | [ ] |
| 1.8 | Call to action with specific next step is present | Important | [ ] |
| 1.9 | Sections flow logically (problem → solution → proof → price → action) | Important | [ ] |
| 1.10 | Total length is appropriate (not padded, not skeletal) | Nice-to-have | [ ] |
| 1.11 | Page numbers or section anchors present for longer proposals | Nice-to-have | [ ] |

---

## Category 2: Scope

| # | Check | Severity | Pass |
|---|-------|----------|------|
| 2.1 | Every requirement from the brief is addressed | Critical | [ ] |
| 2.2 | Explicit exclusions section lists what is NOT in scope | Critical | [ ] |
| 2.3 | No requirement is ambiguously half-addressed | Critical | [ ] |
| 2.4 | Out-of-scope items are listed with a brief rationale | Important | [ ] |
| 2.5 | Change order process is mentioned (even briefly) | Important | [ ] |
| 2.6 | No feature is implied but not scoped (read for "and also...") | Critical | [ ] |
| 2.7 | Scope matches what you actually intend to deliver | Critical | [ ] |

---

## Category 3: Deliverables

| # | Check | Severity | Pass |
|---|-------|----------|------|
| 3.1 | Every deliverable is named specifically (not "phase 1 work") | Critical | [ ] |
| 3.2 | Every deliverable has acceptance criteria | Critical | [ ] |
| 3.3 | Acceptance criteria are testable (observable, not subjective) | Critical | [ ] |
| 3.4 | Every deliverable has an owner assigned | Important | [ ] |
| 3.5 | Every deliverable has a due date or relative week | Important | [ ] |
| 3.6 | STAMP test passes for each deliverable (Specific, Testable, Attributable, Measurable, Precedent-set) | Critical | [ ] |
| 3.7 | No deliverable depends on an undisclosed dependency | Critical | [ ] |
| 3.8 | Deliverables collectively cover the full scope (no gaps) | Critical | [ ] |

---

## Category 4: Pricing

| # | Check | Severity | Pass |
|---|-------|----------|------|
| 4.1 | Total price is clearly stated | Critical | [ ] |
| 4.2 | Pricing model is appropriate for the engagement type | Important | [ ] |
| 4.3 | Calculations are correct (if shown — add them up manually) | Critical | [ ] |
| 4.4 | Payment milestones are tied to deliverables, not calendar dates | Important | [ ] |
| 4.5 | Risk buffer is included (for fixed-price) | Critical | [ ] |
| 4.6 | What happens if scope changes is addressed (change orders) | Critical | [ ] |
| 4.7 | Expenses (travel, licenses, etc.) are addressed | Important | [ ] |
| 4.8 | Pricing is defensible relative to the scope | Important | [ ] |
| 4.9 | Pricing is within the client's stated or inferred budget range | Important | [ ] |

---

## Category 5: Assumptions

| # | Check | Severity | Pass |
|---|-------|----------|------|
| 5.1 | All assumptions are explicitly listed | Critical | [ ] |
| 5.2 | No assumption is buried in prose (they're in a named section) | Important | [ ] |
| 5.3 | Each assumption states what happens if it's wrong | Important | [ ] |
| 5.4 | Assumptions are reasonable given the discovery conversation | Critical | [ ] |
| 5.5 | No hidden assumption protects the client from a risk they own | Critical | [ ] |
| 5.6 | Client-provided inputs are listed (credentials, access, content) | Important | [ ] |

---

## Category 6: Timeline

| # | Check | Severity | Pass |
|---|-------|----------|------|
| 6.1 | Timeline is specific (week numbers or dates) | Critical | [ ] |
| 6.2 | Timeline is realistic given the scope | Critical | [ ] |
| 6.3 | Buffer time exists (timeline is not perfectly optimistic) | Important | [ ] |
| 6.4 | Dependencies between phases are sequential in the timeline | Critical | [ ] |
| 6.5 | Client review periods are reflected (don't show continuous dev) | Important | [ ] |
| 6.6 | Timeline matches the payment schedule milestones | Critical | [ ] |
| 6.7 | Final delivery date matches client's stated deadline | Critical | [ ] |

---

## Category 7: Consistency

| # | Check | Severity | Pass |
|---|-------|----------|------|
| 7.1 | Client name is spelled consistently throughout | Critical | [ ] |
| 7.2 | Contact names and titles are correct | Important | [ ] |
| 7.3 | Numbers add up (totals match line items) | Critical | [ ] |
| 7.4 | Dates are consistent (no conflicting delivery dates) | Critical | [ ] |
| 7.5 | Technology names are spelled correctly (React, TypeScript, not "Typescript") | Nice-to-have | [ ] |
| 7.6 | Deliverable names match between the deliverables table and the timeline | Critical | [ ] |
| 7.7 | Payment amounts sum to total price | Critical | [ ] |
| 7.8 | No leftover placeholder text ([CLIENT NAME], TBD, TODO) | Critical | [ ] |
| 7.9 | Version number and date in header are current | Important | [ ] |

---

## Category 8: Tone

| # | Check | Severity | Pass |
|---|-------|----------|------|
| 8.1 | Tone is professional and confident (not apologetic or overpromising) | Important | [ ] |
| 8.2 | No unexplained jargon | Important | [ ] |
| 8.3 | Tone matches the client's register (enterprise formal vs. startup casual) | Important | [ ] |
| 8.4 | No weasel words ("we'll try to...", "hopefully...", "should be able to...") | Critical | [ ] |
| 8.5 | Claims about your experience are specific, not generic ("8 years" not "extensive") | Nice-to-have | [ ] |
| 8.6 | No passive voice obscuring ownership ("mistakes were made" type constructions) | Nice-to-have | [ ] |

---

## Category 9: Persuasion

| # | Check | Severity | Pass |
|---|-------|----------|------|
| 9.1 | Value proposition is clear in the executive summary | Critical | [ ] |
| 9.2 | The problem statement uses the client's own language (from discovery) | Important | [ ] |
| 9.3 | Relevant past work or case studies are cited | Important | [ ] |
| 9.4 | Differentiators are stated specifically (not "we're passionate about quality") | Important | [ ] |
| 9.5 | The proposal answers "why you, why now" | Important | [ ] |
| 9.6 | Risk mitigation strategies are mentioned where relevant | Important | [ ] |
| 9.7 | The proposal is written for the decision-maker, not the technical contact | Important | [ ] |

---

## Category 10: Call to Action

| # | Check | Severity | Pass |
|---|-------|----------|------|
| 10.1 | A specific next step is stated | Critical | [ ] |
| 10.2 | The next step is client-actionable (not "let me know your thoughts") | Critical | [ ] |
| 10.3 | A validity/expiration date is included | Important | [ ] |
| 10.4 | Contact information is present and correct | Critical | [ ] |
| 10.5 | If DocuSign or contract will be sent, it is mentioned | Nice-to-have | [ ] |
