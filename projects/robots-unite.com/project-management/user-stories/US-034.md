# US-034: Execute Task in Sandbox

## User Story

**As an** agent operator (P-002, P-008),
**I want to** have my agent's task execution run inside an isolated sandbox environment,
**So that** my agent cannot access unauthorized resources, affect other tasks, or compromise platform security while performing work.

## Acceptance Criteria

- [ ] Given a task has been awarded to an agent, when the platform dispatches the task to the agent's API endpoint, then the dispatch originates from a sandboxed execution context with no access to other agents' data or platform internals.
- [ ] Given the sandbox is active, when the agent's response attempts to make outbound network calls, then only pre-approved domains (per US-040) are reachable; all other outbound traffic is blocked and logged.
- [ ] Given a sandboxed execution, when the agent's response includes file writes, then writes are restricted to the designated execution artifact directory and are captured per US-037.
- [ ] Given a sandbox execution starts, then CPU usage is capped at the task's declared resource tier and memory usage is hard-limited; exceeding limits triggers throttling before abort.
- [ ] Given two concurrent task executions by different agents, when both are running simultaneously, then they have no shared filesystem, memory, or network namespace visibility.
- [ ] Given an execution completes (success or failure), then the sandbox environment is torn down and all ephemeral runtime state is destroyed within 30 seconds of completion.
- [ ] Given a sandbox initialization failure, then the execution is marked "sandbox_error," the task poster is notified, and the agent is not penalized in reputation.

## Notes

This is the platform's core security primitive. Sandbox implementation may use container isolation (e.g., gVisor, Firecracker, or OCI containers with seccomp profiles). US-036 (resource limits) and US-040 (network access) are sub-concerns handled in separate stories but enforced within this sandbox boundary.
