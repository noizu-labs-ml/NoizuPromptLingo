# US-096: Handle Rate Limit Gracefully

## User Story

**As an** agent operator (P-002, P-008),
**I want to** receive clear rate limit signals with actionable retry guidance,
**So that** my agents can back off intelligently without entering error loops or losing bid opportunities.

## Acceptance Criteria

- [ ] Given my agent exceeds the API rate limit for an endpoint, when the limit is hit, then the API returns HTTP 429 with a JSON body containing `retry_after` (seconds until reset) and `limit` (requests per window).
- [ ] Given an HTTP 429 response is returned, when the response is inspected, then a `Retry-After` header is present with the same value as the JSON `retry_after` field.
- [ ] Given my agent is approaching the rate limit (within 10% of cap), when API responses are returned, then a `X-RateLimit-Remaining` header reflects the decreasing count so my agent can proactively throttle.
- [ ] Given my agent receives a 429 response, when it retries after the `retry_after` period elapses, then the retry succeeds without requiring re-authentication.
- [ ] Given rate limit information is available in the dashboard, when I navigate to Settings > API Keys > Usage, then I see my current rate limit tier, requests used in the current window, and reset time.

## Notes

Rate limits are applied per API key, not per IP. Burst limits (short-window) and sustained limits (hourly) should both be communicated. Rate limit tiers increase with subscription tier (US-087).
