# US-062: Database Schema and Migration Framework

As a developer,
I want a robust SQLite database schema with a migration framework,
so that data persists correctly and schema changes can be applied safely without losing user data.

## Scenario: Initial database schema creation
Given the application is launched for the first time
When the database manager initializes
Then a SQLite database should be created with the following tables: clipboard_items, favorites, metadata, and settings
And all appropriate indexes should be created on frequently queried columns

## Scenario: Clipboard items table structure
Given the clipboard_items table is defined
When an item is stored
Then the table should contain: id (primary key), content, content_type, source_app, timestamp, size, and hash
And the content field should handle large text and binary data efficiently

## Scenario: Automatic version tracking
Given the database is initialized
When the database manager starts
Then a schema_version table should exist with the current version number
And migration scripts should be associated with specific version numbers

## Scenario: Apply pending migrations on startup
Given the database has version 1 and version 2 migrations are available
When the application starts
Then pending migrations should be detected and applied automatically
And the schema_version table should be updated to reflect the new version

## Scenario: Migration rollback capability
Given a migration fails during deployment
When the application encounters a migration error
Then the migration framework should roll back all changes applied in that transaction
And leave the database in a consistent, pre-migration state

## Scenario: Backup before migration
Given a database migration version is 2 or higher (significant changes)
When the migration is about to be applied
Then a backup of the existing database should be created at a backup location
And the backup should be retained for 7 days in case of rollback

## Scenario: Migration for new type detection field
Given clipboard_items currently stores content_type as a string
When the application introduces richer content type metadata
Then a migration should add content_subtype, confidence_score, and manually_flagged fields
And the migration should populate subtype based on heuristics for existing records

## Scenario: Add full-text search support
Given users frequently need to search clipboard content
When the FTS migration is applied
Then a virtual table (clipboard_items_fts) should be created using FTS5
And triggers should maintain FTS index whenever clipboard_items are modified

## Scenario: Database connection pooling
Given the application may have concurrent database access
When the database manager manages connections
Then a connection pool of maximum 5 connections should be maintained
And connections should be properly closed on app termination

## Scenario: SQLite performance optimizations
Given clipboard_items table grows large (10,000+ items)
When the database is queried for recent items
Then appropriate indexes should exist on timestamp, content_type, and hash columns
And WAL (Write-Ahead Logging) mode should be enabled for better concurrency

## Notes
- **Persona**: developer
- **T-Shirt Size**: L
- **Complexity**: high
- **Risks**: Migration failures could corrupt user data; backup storage management; connection pool exhaustion
- **Dependencies**: None (foundational)
