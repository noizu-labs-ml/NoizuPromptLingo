# Tom Brennan — CS Instructor ("The Educator")

**Type:** Tertiary
**Segment:** Education — Instructor
**Pipeline entry:** Phase 1 (Sketch)
**Likely exit:** Phase 3 (Ink) — uses generated projects as teaching material

---

## Demographics

- **Age:** 45
- **Role:** Computer Science professor at a state university, teaches software engineering
- **Location:** Portland, OR
- **Income:** $105K
- **Tech comfort:** Expert — PhD in CS, but hasn't shipped production code in years

## Quote

> "Students learn nothing from toy projects. But real projects take a semester just to scaffold. I need something in between."

## Goals

1. Generate realistic project scaffolds for student assignments and capstone projects
2. Demonstrate the full software lifecycle (plan → design → build → ship) in a 15-week semester
3. Give students structured specs so they learn implementation, not requirements gathering
4. Create varied projects each semester so students can't copy last year's solutions

## Frustrations

- Writing new project specs every semester is exhausting
- Students skip the planning phase and jump straight to code — then build the wrong thing
- Capstone projects fail because teams can't agree on scope
- Existing starter templates are either too trivial or too complex

## Behaviors

- Publishes course materials on GitHub and personal site
- Evaluates tools for classroom fit: must work for 30 students, can't require paid accounts
- Prefers tools with clear, inspectable output — no black boxes
- Reads ACM education papers, attends SIGCSE

## Scenario

Tom creates 5 different project specs in noizu.ink for his capstone class. Each team gets a different project: a recipe app, a study group finder, a campus event tracker, etc. The Sketch phase produces PRDs with personas and stories. Tom reviews and adjusts the scope for appropriate difficulty. He exports the PRDs as markdown and the Draft mockups as reference. Students implement against the stories. Tom uses the generated acceptance criteria as grading rubrics.
